# Alpine Club — Система учета альпинистских восхождений

Веб-приложение для автоматизации учета горных вершин, регистрации участников, комплектования групп восхождения и ведения отчетности.

---

## 🛠 Стек технологий
* **Бэкенд:** Python, Django, Django REST Framework (DRF)
* **База данных:** MySQL
* **Конфигурация:** python-dotenv

---

## 📊 Схема данных и Описание API

### Схема данных (Реляционная модель 3НФ)
1. **Альпинисты** (`id`, `Фамилия`, `Имя`, `Дата рождения`, `Разряд`, `Номер телефона`, `E-mail`, `Пройдена ли школа`, `Пройден ли тест`)
2. **Горы** (`id`, `Название горы`, `Страна`, `Регион`, `Рекомендуемый разряд`, `Высота`)
3. **Группы** (`id`, `Дата формирования`, `Название группы`, `Максимальное количество человек`, `id горы`)
4. **Альпинисты-Группы** (`id`, `id_альпиниста`, `id группы`, `роль`)
5. **Восхождения** (`id`, `id Группы`, `Дата и время начала восхождения`, `Коментарий`, `Оценка восхождения`, `Результат`)

### Описание REST API
Проект предоставляет эндпоинты через Django REST Framework по префиксу `/api/`:
* `GET /api/mountains/` — каталог горных вершин.
* `GET, POST /api/climbers/` — управление альпинистами.
* `GET, POST, PUT, DELETE /api/groups/` — управление группами походов.
* `GET, POST, DELETE /api/group-members/` — управление составом участников.
* `GET, POST /api/ascents/` — учет восхождений.
* **Служебный эндпоинт:** `GET /health/` — проверка связи с СУБД (возвращает `{"status": "ok"}`).

## 📋 Правила внесения изменений и регламент разработки

### 1. Запрещенные действия
* **Запрещено** отправлять код напрямую в основную ветку `main`. Разработка ведется только в изолированных ветках (`feature/...`).
* **Запрещено** добавлять в публичный репозиторий конфиденциальные файлы (пароли `.env`, папки `venv/`).

### 2. Обязательные команды проверки
Перед созданием запроса на слияние выполняются локально:
* Проверка конфигурации: `python manage.py check`
* Применение миграций: `python manage.py migrate`
* Запуск сервера и проверка Health Check: `python manage.py runserver` с запросом на `http://127.0.0.1:8000/health/`.

### 3. Порядок приемки изменений (Workflow)
1. Создание задачи.
2. Создание отдельной ветки от `main`.
3. Фиксация изменений через осмысленные коммиты (`feat:`, `docs:`).
4. Отправка ветки на сервер и оформление Pull Request.
5. Проверка изменений (Code Review) и слияние (Merge) в `main`.

## 🔒 Безопасность и развертывание (Инфраструктурные требования)

Проект спроектирован с учетом базовых принципов информационной безопасности для многосерверной среды (разделение на App и DB серверы):

1. **Изоляция прав (Non-root execution):**
   * Веб-приложение на сервере задействует выделенного непривилегированного системного пользователя (`appuser`). Запуск и обслуживание сервисов под учетной записью `root` запрещены.

2. **Сетевой экран (Firewall / nftables):**
   * на обоих серверах настроен `nftables` с политикой блокировки входящего трафика по умолчанию (`drop`);
   * открыты только необходимые порты:
     * **порт 22 (TCP):** SSH-доступ для администраторов;
     * **порт 8000 (TCP):** доступ к веб-приложению (Gunicorn) на сервере приложения;
     * **порт 3306 (TCP):** доступ к СУБД (MariaDB) на сервере базы данных — открыт **исключительно** для IP-адреса сервера приложения.

3. **Защита конфиденциальных данных:**
   * cекретные параметры (`SECRET_KEY`, доступы и пароли к базе данных) вынесены в изолированный файл окружения `.env`;
   * файл `.env` защищен локальными правами доступа (`chmod 600`) и строго исключен из системы контроля версий (`.gitignore`). В репозитории содержится только безопасный шаблон конфигурации (`.env.example`).
